# Scout Output Schema

This reference defines how ChatGPT should interpret outputs generated by the
`arxiv-research-scout` backend.

Use this file together with `../SKILL.md`.

## 1. Research Digest

Typical location:

```text
reports/digests/YYYY-MM-DD.md
```

A digest summarizes one completed or partially completed scout run.

### Run Summary

Expected fields:

- `Generated (UTC)` — UTC timestamp when the digest was generated.
- `Provider` — LLM provider used for paper analysis.
- `Model` — model identifier used for paper analysis.
- `Run status` — `complete` or `partial`.

Interpretation:

- `complete` means the digest was written successfully and no paper-processing
  failures remained for that run.
- `partial` means at least one selected paper failed during processing.
- A complete run may contain zero successfully analyzed papers.
- A complete run with zero selected papers is valid and does not imply an LLM
  call occurred.

Do not infer scientific quality from run status.

### Retrieval Summary

Expected fields:

- `Candidates retrieved`
- `Recent papers`
- `After ID dedup`
- `Unprocessed papers`
- `Relevant papers`
- `Selected for analysis`
- `Successfully analyzed`
- `Failed`

Interpretation:

- `Candidates retrieved` is the number returned by the arXiv retrieval stage.
- `Recent papers` is the number remaining after the configured lookback window.
- `After ID dedup` is the number remaining after normalized arXiv ID
  deduplication.
- `Unprocessed papers` excludes papers already recorded in persistent state.
- `Relevant papers` is the number that passed the configured relevance
  threshold.
- `Selected for analysis` is the number selected after ranking and
  `max_papers`.
- `Successfully analyzed` is the number of paper transactions that completed.
- `Failed` is the number of selected papers that failed during processing.

Never infer hidden papers or missing retrieval results from these counts.

## 2. Per-Paper Digest Entry

A successfully analyzed paper can include:

- Title
- arXiv ID
- Authors
- Published timestamp
- Evidence level
- Confidence
- Abstract URL
- Paper report path
- Methodology
- Evaluation
- Innovation
- Datasets
- Metrics
- Key Results
- Limitations
- Processing Note, when applicable

Use the values exactly as available.

Do not infer fields that are absent.

## 3. Per-Paper Report

Typical generated reports contain the following sections.

### Paper Information

May include:

- arXiv ID
- Authors
- Published
- Updated
- Categories
- Abstract URL
- PDF URL

These are metadata, not model-generated research conclusions.

### Analysis Information

May include:

- Provider
- Model
- Evidence level
- Confidence
- PDF status

`PDF status: Available` means PDF-derived evidence was available to the analysis
pipeline.

A fallback status means PDF processing was unavailable or incomplete and the
analysis may rely more heavily on abstract-level evidence.

## 4. Structured Analysis Fields

### Methodology

Meaning:

A grounded summary of what the paper proposes and how the method works.

May include, only when supported:

- pipeline stages
- model architecture
- algorithms
- preprocessing
- training strategy
- inference procedure

Do not add architecture details, training settings, or implementation details
that are not present in the report evidence.

### Evaluation

Meaning:

A grounded summary of how the method was evaluated.

May include, only when supported:

- datasets
- dataset sizes
- train/validation/test protocol
- cross-validation
- comparison methods
- metrics
- statistical tests
- numerical results

Do not infer an evaluation protocol from common practice in the field.

### Innovation

Meaning:

A summary of the technical or methodological contribution supported by the
available evidence.

Do not exaggerate novelty.

Terms such as:

- `first`
- `novel`
- `state-of-the-art`
- `outperforms`

must not be introduced unless the available evidence supports them.

### Datasets

Meaning:

Dataset names explicitly identified by the analysis.

Rules:

- Keep official dataset names.
- Do not infer datasets from the research topic.
- Do not infer LUNA16, LIDC-IDRI, LNDb, or any other dataset merely because the
  paper concerns lung nodules or CT.

### Metrics

Meaning:

Evaluation metrics or statistical measures explicitly identified in the
analysis.

Examples can include:

- FROC
- sensitivity
- false positives per scan
- Dice score
- AUROC
- p-value
- Cohen's d

Only list metrics actually present in the scout output.

Do not convert qualitative claims into quantitative metrics.

### Key Results

Meaning:

Important findings explicitly supported by the available evidence.

Rules:

- Preserve reported numerical values accurately.
- Do not estimate missing numbers.
- Do not convert qualitative improvement into invented percentages.
- Do not claim statistical significance unless a reported test supports it.

### Limitations

Meaning:

Limitations identified from the available analysis evidence.

Distinguish between:

1. limitations explicitly stated by the paper authors;
2. limitations inferred because important evidence was unavailable.

Never present an inferred limitation as an author-stated limitation.

## 5. Evidence Levels

### `full_text`

Substantial PDF-derived paper evidence was available.

This does not guarantee that every paper detail was successfully extracted.

### `partial_text`

Some useful PDF-derived evidence was available, but important sections or
details were incomplete.

Use more cautious language than for `full_text`.

### `abstract_only`

Analysis relied primarily on arXiv metadata and abstract-level evidence.

Do not claim detailed architecture, training, experimental-protocol, or
numerical information unless it is explicitly present in that evidence.

## 6. Confidence

Confidence refers to confidence in the available evidence for producing the
analysis.

It does not mean:

- confidence that the paper is correct;
- confidence that the method generalizes;
- confidence that the paper is scientifically strong.

Typical values:

- `high`
- `medium`
- `low`

Interpret confidence together with evidence level.

## 7. Processing Failures

A digest may contain a `Processing Failures` section.

Each failure can include:

- arXiv ID
- paper title
- error message

Interpretation:

- successfully processed papers from the same run remain valid;
- failed papers are not treated as successfully processed;
- failed papers can remain eligible for a later retry;
- a run containing failures should normally be interpreted as `partial`.

Do not infer the scientific content of a failed paper from the error message.

## 8. Processing Notes

A paper may include a processing note indicating that PDF processing failed or
was incomplete and fallback evidence was used.

When a fallback is reported:

- mention the fallback when it materially affects the answer;
- avoid detailed claims that would normally require full-text evidence;
- do not silently treat the report as equivalent to a full-text analysis.

## 9. Persistent State

Typical location:

```text
.state/state.json
```

Expected structure:

```json
{
  "schema_version": 1,
  "last_successful_run_utc": null,
  "processed_ids": []
}
```

### `schema_version`

Version of the state-file schema.

Do not treat it as a research result.

### `last_successful_run_utc`

UTC timestamp of the most recent run that completed the run-level success
transaction.

A run is marked successful only after:

1. paper processing is complete;
2. the digest is written successfully;
3. no unresolved paper failures remain;
4. the final state save succeeds.

A missing or old timestamp does not necessarily mean that no individual paper
was successfully processed.

### `processed_ids`

Normalized arXiv IDs of successfully processed papers.

Version suffixes are normalized.

For example:

```text
2608.12345v1
2608.12345v2
2608.12345v3
```

represent the same normalized paper identity for processed-state purposes.

Do not infer which paper version was analyzed solely from the normalized state
entry.

## 10. Scheduling Semantics

The GitHub Actions workflow may wake more frequently than the research run is
due.

The application uses configuration such as:

```yaml
schedule:
  run_every_days: 3
```

to decide whether a scheduled research run should proceed.

Therefore:

- a GitHub Actions execution can legitimately skip research work;
- a skipped run is not a failure;
- a skipped run should not require an LLM API call;
- no new digest is expected for a skipped run.

## 11. Provider Semantics

The project supports:

- DeepSeek
- OpenAI

The provider/model recorded in a report describes which provider/model produced
that structured analysis.

Do not assume two provider outputs are equivalent.

Do not prefer one provider's result merely because of provider identity.
Compare only the evidence and output quality when the user asks for a
comparison.

## 12. Relevance Semantics

The scout uses configurable rule-based relevance filtering before LLM analysis.

Configuration can include:

- core terms
- target terms
- supporting terms
- deprioritized terms
- minimum score
- high-relevance score

If an actual relevance score is available, it may be reported.

If the score is not available, explain relevance qualitatively from the
available title, abstract, report, and configuration.

Never invent a relevance score.

## 13. Strict No-Inference Fields

Never invent or silently infer any of the following:

- dataset names
- sample sizes
- patient counts
- scan counts
- nodule counts
- class counts
- train/validation/test splits
- fold assignments
- augmentation
- preprocessing
- architecture components
- optimizers
- learning rates
- epoch counts
- loss functions
- parameter counts
- FLOPs
- runtime
- memory usage
- baselines
- ablation studies
- metrics
- statistical tests
- numerical performance
- statistical significance
- author-stated limitations
- novelty claims

If the information is absent, say:

- `not reported`,
- `not available in the scout output`, or
- an equivalent statement in the user's language.

## 14. Recommended Answer Mapping

When the user asks for a research update, map scout output into:

1. Run status
2. Retrieval/analyzed counts
3. Paper-by-paper summaries
4. Cross-paper observations, only when supported by multiple papers
5. Processing failures or evidence fallbacks

When the user asks for a specific paper, map into:

1. Research objective
2. Methodology
3. Evaluation
4. Innovation
5. Datasets
6. Metrics
7. Key Results
8. Limitations
9. Evidence level and confidence

When the user asks for trends, use multiple papers or digests and clearly state
the evidence window.

## 15. Final Validation Checklist

Before answering from scout outputs:

- Confirm the newest relevant digest/report was actually inspected.
- Verify each numerical claim against the available output.
- Verify dataset and metric names are explicitly present.
- Distinguish author-stated limitations from inferred limitations.
- Avoid exaggerated novelty language.
- Mention partial/abstract-only evidence when relevant.
- Surface processing failures when they affect completeness.
- Never reveal API keys or secret values.
- Never claim a backend command or GitHub Action was executed unless a tool
  result confirms it.
